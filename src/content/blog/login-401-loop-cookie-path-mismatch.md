# 로그인은 되는데 재로그인은 안 된다? — 세션 쿠키 삭제 Path 불일치로 인한 401 무한루프 트러블슈팅

## 증상

관리자 페이지에서 이상한 로그인 버그를 만났다.

- 이미 한 번 로그인했던 계정으로 **다시 로그인하면 계속 실패**한다.
- 응답은 항상 이거였다.

```json
{
  "status": 401,
  "message": "Session expired. Please login again."
}
```

- 그런데 **Swagger에서 똑같은 계정으로 로그인하면 성공**한다.
- 브라우저 쿠키를 수동으로 지우면 그제서야 로그인이 된다.

"프론트 코드가 잘못됐나?" 싶었지만, 로그인 요청 코드는 지극히 평범했다.

```ts
async function login(username: string, password: string) {
  const { data } = await api.post('auth/login-proc', { username, password });
  // ...
}
```

특별할 게 없다. 그렇다면 **Swagger는 되고 브라우저는 안 되는 차이**가 어디서 오는지가 핵심이다.

## 첫 번째 단서: 인증은 쿠키 기반이다

이 프로젝트의 인증은 토큰이 아니라 **세션 쿠키(JSESSIONID / ADMINSESSIONID)** 기반이었다. 그리고 axios 인스턴스에 `withCredentials: true`가 걸려 있었다.

```ts
const api = axios.create({
  baseURL: '/api/admin/v1',
  withCredentials: true, // 요청마다 브라우저 쿠키를 자동 첨부
});
```

`withCredentials: true`는 **모든 요청에 브라우저가 가진 쿠키를 자동으로 실어보낸다.** 로그인 요청도 예외가 아니다.

여기서 Swagger와의 차이가 설명된다.

- **브라우저**: 예전 로그인 때 발급받은 (이미 만료된) 세션 쿠키를 로그인 요청에 함께 보낸다.
- **Swagger**: 그 쿠키를 공유하지 않으므로 요청이 깨끗하게 도착한다 → 정상 로그인.

즉 백엔드의 세션 검증 필터가 요청에 담긴 **만료된 세션 쿠키를 먼저 발견하고**, 자격증명을 확인하기도 전에 `401 Session expired`를 던지고 있었다.

## 두 번째 의문: 그런데 왜 "무한" 반복되는가

여기까지는 "만료된 쿠키가 문제"라는 것까지 이해됐다. 하지만 이상하다.

보통 이런 경우 서버는 401을 주면서 **만료된 쿠키를 삭제**하라고 응답한다. 그러면 다음 시도에는 쿠키가 없으니 로그인이 성공해야 한다. 그런데 몇 번을 시도해도 계속 401이었다.

응답 헤더를 열어봤더니 서버는 실제로 쿠키를 지우려 하고 있었다.

```
Set-Cookie: JSESSIONID=; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:10 GMT; Path=/; SameSite=None  ⚠️
Set-Cookie: ADMINSESSIONID=; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:10 GMT; Path=/
```

`Max-Age=0`, `Expires=1970` — 쿠키 삭제의 정석적인 방법이다. 그런데도 쿠키가 안 지워진다. **삭제 요청을 보냈는데 브라우저가 삭제를 하지 않는 것**이다.

## 결정적 단서: 쿠키는 Path까지 일치해야 지워진다

브라우저가 쿠키를 삭제(덮어쓰기)할 때는 단순히 **이름**만 보는 게 아니다. **이름 + Domain + Path** 조합으로 "같은 쿠키"인지 판단한다. 이 조합이 다르면 브라우저는 서로 다른 쿠키로 취급하고, 삭제 헤더는 무시된다.

그래서 로그인 **성공** 시 발급되는 쿠키의 속성과, 401 응답에서 **삭제**하려는 쿠키의 속성을 나란히 비교했다.

| 구분              | Path             | Secure | SameSite |
| ----------------- | ---------------- | ------ | -------- |
| 로그인 성공(세팅) | **`/api/admin`** | ✅     | None     |
| 401 삭제 시도     | **`/`**          | ❌     | (없음)   |

범인이 드러났다. 쿠키는 `Path=/api/admin`에 저장돼 있는데, 서버는 `Path=/`로 삭제를 시도하고 있었다. **Path가 달라서 삭제가 매칭되지 않았던 것이다.**

그래서 흐름은 이렇게 무한히 돌고 있었다.

1. 브라우저에 만료된 `ADMINSESSIONID`(Path=/api/admin)가 남아있음
2. 로그인 요청에 그 쿠키가 실려감 → 서버가 만료 세션 감지 → `401`
3. 서버가 `Path=/`로 삭제 시도 → **Path 불일치로 브라우저가 무시**
4. 쿠키가 그대로 남음 → 다음 로그인에도 다시 1번으로 → 무한 401

쿠키를 수동으로 지웠을 때만 로그인이 됐던 이유도 이걸로 설명된다.

## 근본 원인

정리하면, **프론트엔드 로직의 문제가 아니라 백엔드가 쿠키를 삭제할 때 세팅 때와 다른 Path를 사용한 버그**였다.

- 세팅: `Path=/api/admin`
- 삭제: `Path=/`

쿠키 삭제는 세팅 때와 **동일한 Path/Domain**으로 해야만 적용된다. 이건 [RFC 6265](https://datatracker.ietf.org/doc/html/rfc6265)에 정의된 쿠키 매칭 규칙이다.

## 해결

### 근본 해결 (백엔드)

삭제용 `Set-Cookie`를 세팅 때와 **동일한 속성**으로 내려보내면 된다.

```
Set-Cookie: ADMINSESSIONID=; Max-Age=0; Path=/api/admin; Secure; HttpOnly; SameSite=None
```

덤으로 발견한 것 하나 더. JSESSIONID 삭제 헤더에는 `SameSite=None`이 있는데 `Secure`가 빠져 있어 브라우저 경고(⚠️)가 떠 있었다. **`SameSite=None` 쿠키는 반드시 `Secure`와 짝**이어야 하며, 그렇지 않으면 그 Set-Cookie 자체가 브라우저에서 거부된다. 이것도 `Secure`를 추가해야 한다.

추가로, 애초에 `login-proc` 엔드포인트는 기존 세션 만료 여부와 무관하게 인증을 처리해야 정상이다. **세션 만료 검증 필터에서 로그인 엔드포인트를 제외**하면(= Swagger가 정상 동작하는 상태) 이 문제 자체가 발생하지 않는다.

### 로컬 개발 완화책 (프론트)

백엔드 수정을 기다리는 동안 로컬 개발을 막을 순 없으니, Vite 프록시에서 응답 쿠키의 Path를 통일해주는 워크어라운드를 넣었다.

```js
// vite.config.mjs
proxy: {
  '/api': {
    target: env.VITE_API_BASE_URL,
    changeOrigin: true,
    cookieDomainRewrite: '',
    // BE가 쿠키를 Path=/api/admin으로 세팅하는데 삭제는 Path=/로 내려보내 매칭 실패 → 만료쿠키가 안 지워짐.
    // 로컬 한정으로 모든 쿠키 Path를 '/'로 통일해 세팅/삭제 Path를 일치시킴.
    cookiePathRewrite: '/',
  },
},
```

`cookiePathRewrite: '/'`로 세팅되는 쿠키와 삭제되는 쿠키의 Path를 모두 `/`로 맞추면, 삭제가 정상적으로 매칭된다. 단 이건 운영 환경(same-origin이라 프록시 없음)에는 적용되지 않으므로 **어디까지나 로컬 전용**이고, 근본 해결은 백엔드 몫이다.

> ⚠️ 적용 후에는 Vite 개발 서버를 재시작하고, 이미 `Path=/api/admin`으로 박혀있는 기존 쿠키는 **한 번만 수동 삭제**해야 한다. 그 이후부터는 새 쿠키가 `Path=/`로 저장되어 스스로 정리된다.

## 배운 점

- **`withCredentials: true`는 로그인 요청에도 쿠키를 실어보낸다.** "로그인인데 왜 기존 세션이 영향을 주지?"라는 함정에 빠지기 쉽다.
- **쿠키 삭제는 이름만으로 되지 않는다.** 세팅 때와 동일한 `Domain`, `Path`가 아니면 브라우저는 삭제를 무시한다. 삭제가 안 될 땐 세팅/삭제 헤더의 속성을 나란히 비교하자.
- **`SameSite=None`은 항상 `Secure`와 함께.** 아니면 그 쿠키는 브라우저가 조용히 버린다.
- **"Swagger는 되는데 브라우저는 안 된다"는 대부분 쿠키 차이다.** 이 한 문장이 디버깅의 방향을 잡아줬다.
